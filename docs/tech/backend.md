# Backend

## Проекты

Решение `backend/FastArena.sln`, проекты в `backend/src/`:

- `FastArena.Core` — доменные модели (`Domain/`), контракты сервисов и хранилищ (`Interfaces/`), сервисы (`Services/`), входные модели сервисов (`Models/`), доменные исключения (`Exceptions/`). Не зависит от других проектов.
- `FastArena.Dal` — EF Core и PostgreSQL: `ApplicationContext`, сущности `*Dal` (`Entities/`), профили маппинга (`Profiles/`), реализации хранилищ (`Storages/`). Зависит от Core.
- `FastArena.WebApi` — контроллеры, выходные DTO (`Dtos/`), входные модели контроллеров (`Models/`), профили маппинга (`Profiles/`), выдача токенов и хеширование паролей (`Providers/`). Зависит от Core.
- `FastArena.WebHost` — точка запуска: `Program`, `Startup`, регистрация зависимостей и конфигурация по группам (`Configs/`), сидеры и их регистрация (`Services/Seeders/`), статика (`wwwroot/`). Собирает Core, Dal и WebApi.
- `FastArena.Core.Tests` — тесты Core.
- `FastArena.ApiClientGenerator` — генератор API-клиента; от остальных проектов не зависит.

Dal и WebApi друг о друге не знают; связывает их только WebHost.

## Обработка запроса

Контроллер берёт id пользователя из токена (`AuthProvider.GetCurrentUserIdFromAccessor`), переводит входную модель в модель Core и вызывает сервис через интерфейс из `Core/Interfaces/App`. Сервис работает с данными через интерфейсы хранилищ из `Core/Interfaces/Storages`, реализованные в Dal. Результат сервиса контроллер переводит в DTO профилем WebApi.

Доменные исключения Core переводятся в HTTP-ответ в самом контроллере блоком `try/catch`: `ActionDeniedException` — в 409, `EntityNotFoundException` — в 404. Глобального обработчика нет; непойманное исключение даёт 500.

Сервисы и хранилища регистрируются в `WebHost/Configs` со временем жизни scoped, сидеры — в `Services/Seeders/SeederServiceExtensions`. Singleton — обработчики эффектов, их реестр и хранилище сессий активности. Новый сервис или хранилище без регистрации в `Configs` не разрешается при запросе.

## Модели и маппинг

Данные существуют в трёх представлениях: сущности Dal, доменные модели Core и DTO WebApi. Переход между ними выполняют статические профили `*Profile(s).Map(...)`, написанные вручную: профили Dal переводят сущности в доменные модели и входные модели Core в сущности, профили WebApi — доменные модели в DTO.

Вложенные объекты и коллекции профиль заполняет только при `deep = true`; по умолчанию вложенные объекты равны `null`, коллекции пусты. Исключение — `ItemProfiles` в Dal: загруженные коллекции предмета он заполняет независимо от флага.

Хранилища загружают вложенные сущности цепочками `Include`/`ThenInclude`. Вложенное поле, не попавшее в цепочку, приходит пустым. Поэтому новое вложенное поле в ответе требует расширения цепочки `Include` в хранилище и `deep` в профилях Dal и WebApi, через которые оно проходит. Пропуск любого из этих изменений ошибки не вызывает.

## Схема базы данных

Схема задаётся в `ApplicationContext.OnModelCreating()`. Миграции EF не используются: конструктор `ApplicationContext` вызывает `Database.EnsureCreated()`, который создаёт базу со схемой, если базы нет, и не меняет существующую. Изменение схемы попадает в базу только после её пересоздания.

## Начальные данные

`SeederRunner` выполняется при каждом запуске backend и по порядку заполняет портреты, монстров, связь монстров с портретами, предметы и награды монстров. Источники: файлы изображений в `wwwroot/assets/portraits` (тег `Heroes`) и `wwwroot/assets/creatures` (тег `Monsters`), классы `Seeders/Data/ItemSeedData` и `Seeders/Data/MonsterSeedData`, таблица наград в `MonsterRewardSeeder`. Монстр получает портрет по имени файла из `MonsterSeedData.PortraitFileByName`.

Условие добавления у сидеров разное:

- портреты — для тега, у которого портретов нет;
- монстры — отсутствующие в базе по id и по имени;
- связь монстров с портретами — пересчитывается при каждом запуске;
- предметы — только в пустую таблицу;
- награды — для монстра, у которого записей наград нет.

Поэтому в существующую базу попадают новые монстры с их наградами и изменения привязки портретов. Изменения засеянных монстров и наград, изменения и добавления предметов, новые портреты тега, у которого портреты уже есть, в неё не попадают. Награда нового монстра, ссылающаяся на новый предмет, нарушает внешний ключ, и запуск backend завершается ошибкой.

## Аутентификация

`AuthProvider` выдаёт JWT, подписанный симметричным ключом, с claims логина и id пользователя (`NameIdentifier`). Параметры берутся из секции конфигурации `AuthOptions`: `Issuer`, `Audience`, `Lifetime` в минутах, `SecretKey`. Проверка токена — издатель, аудитория, срок жизни, подпись — настраивается в `WebHost/Configs/AuthConfig`. `PepperedPasswordHasher` хеширует пароль через `PasswordHasher` из ASP.NET Identity, добавляя к нему секрет `AuthOptions:HashSecret`. Закрытые эндпоинты помечены `[Authorize]`.

## Тесты

`FastArena.Core.Tests` на xUnit ссылается только на Core. `Unit/` проверяет обработчики эффектов и сервисы по отдельности, `Integration/` — сценарии `MonsterFightService` целиком. Зависимости подменяются вложенными классами-заглушками, реализующими интерфейсы Core; библиотека моков не используется.

Часть тестов `MonsterFightService` вызывает его закрытые статические методы через reflection по имени. Переименование такого метода ломает тест только при выполнении.
